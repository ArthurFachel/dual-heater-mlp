# Functional SlowHeat and Functional DualHeat contract

Contrato dos dois mecanismos centrais do projeto. A primeira metade especifica
**Functional SlowHeat** (proteção seletiva por importância funcional); a
segunda especifica **Functional DualHeat**, que é definido como FastHeat de
ativação somado ao Functional SlowHeat, e por isso não faz sentido isolado.

Functional SlowHeat is the current experimental method. Historical pilot
artifacts were generated by the previous activation-magnitude implementation
and are not efficacy results for this version.

## Scale-invariant functional utility

For neuron pre-activation `z_i` and loss `L`, the instantaneous utility is:

```text
u_i = sum_samples |z_i * dL/dz_i|
u_normalized,i = u_i / (mean_j(u_j) + eps)
```

The layer stores an online mean followed by an EMA of this normalized signal.
For a positively homogeneous neuron, reparameterizing its incoming weights by
`c` and its outgoing weights by `1/c` leaves `z_i * dL/dz_i` unchanged. A dead
ReLU receives zero gradient and therefore zero utility even if its negative
pre-activation magnitude is large.

The statistic is collected by an activation-gradient hook. A forward without
backward does not change task importance. The normalization removes global
loss and batch-reduction scale, but utility remains a first-order local proxy.

## Capacity-budgeted consolidation

`importance_memory` stores persistent evidence using `max`, `mean` or `sum`.
`slow_heat` is a derived `[0, 1]` protection vector. After consolidation, the
highest-utility units are selected subject to:

```text
protected_count <= floor((1 - plasticity_budget) * unit_count)
```

This guarantees at least the requested free capacity up to integer rounding.
Calling `consolidate()` without a completed backward is rejected.

`adapt_capacity(acquisition_score=..., target_score=...)` implements a bounded
proportional controller. If validation acquisition is below target, it raises
the plasticity budget; if acquisition is above target, it permits more
protection. Only a separately held-out validation stream may drive this API.

## Bidirectional factorized protection

For weight `W_l[i,j]`, the optimizer combines the output-neuron factor of layer
`l` with the input-neuron factor from layer `l-1`:

```text
M_l[i,j] = min(m_output_l[i], m_output_l_minus_1[j])
```

Thus an important neuron protects its incoming row and the corresponding
columns in the next layer. The output classifier is a `SlowHeatLinear` by
default. `register_slow_heat_model(model)` validates and registers the whole
sequential topology; checkpoint metadata records the source position of every
factorized connection and fails closed on a mismatched topology.

## Optimizer-state semantics

Both optimizers first compute a native update and then apply:

```text
theta_new = theta_old + M * (theta_native - theta_old)
```

The default `state_policy="follow_update"` applies the same interpolation to
every tensor-valued state with parameter shape, including AdamW `exp_avg`,
`exp_avg_sq`, optional AMSGrad state and SGD momentum:

```text
state_new = state_old + M * (state_native - state_old)
```

Scalar step counters remain global because PyTorch AdamW does not maintain a
per-weight age. `state_policy="native"` is retained as a declared ablation.
The policy is stored in optimizer checkpoints, and loading with a different
policy is rejected.

## Required ablations

- functional utility versus activation magnitude and random utility;
- factorized versus row-only protection;
- fixed budget, adaptive budget and no budget;
- `follow_update` versus `native` state policy;
- protected versus unprotected output classifier;
- MAX, mean and sum evidence consolidation;
- global reduced learning rate and no-consolidation controls.

# Functional DualHeat

Functional DualHeat é definido neste repositório como:

```text
FastHeat de ativação + Functional SlowHeat
```

Ele não é a implementação histórica de `DualHeatLinear`/`DualHeatMLP`. Essas
APIs continuam inalteradas apenas para compatibilidade com checkpoints e
experimentos antigos.

## FastHeat

Para uma ativação oculta `h`, cada unidade ou canal mantém um buffer
`fast_heat` não treinável. A magnitude pós-ativação é normalizada dentro da
camada:

```text
a_i      = mean(|h_i|)
r_i      = a_i / (mean_j(a_j) + eps)
others_i = mean_{j != i}(fast_heat_j)
gate_i   = 1 / (1 + gamma * others_i)
h'_i     = gate_i * h_i
fast_heat_i <- ReLU(alpha*fast_heat_i + (1-alpha)*(r_i-delta))
```

O forward usa o estado anterior e somente depois atualiza o buffer. Em
`train()` o gate é aplicado e atualizado. Em `eval()` o gate continua aplicado,
mas o estado fica congelado; validação e teste não alteram o modelo. FastHeat
não é reiniciado nas fronteiras de tarefa e é salvo pelo `state_dict`.

Os gates aparecem apenas nas ativações ocultas: após cada ativação do MLP;
após cada ReLU e antes do pooling na CNN pequena e VGG11; e após o
`GroupNorm+ReLU` do stem e cada `soma residual+ReLU` no ResNet18. A cabeça de
logits nunca recebe gate.

As classes públicas são `FunctionalDualHeatMLP`, `FunctionalDualHeatCNN`,
`FunctionalDualHeatVGG11` e `FunctionalDualHeatResNet18`. Cada modelo expõe
`get_fast_states()` e `reset_fast_heat()`.

## Piloto e benchmarks DualHeat

O piloto usa três seeds fixas, cinco épocas por tarefa e a grade completa de
`alpha={0.90,0.97}`, `gamma={0.5,2.0}` e `delta={0.0,0.5}` em VGG11 e ResNet18.
A seleção consulta exclusivamente a acurácia Class-IL final de validação. O
manifesto congelado é obrigatório para os benchmarks principais de 13 métodos.

```bash
python run_all_tests.py \
  --num-seeds 10 \
  --sections functional-dualheat-pilot \
    split-cifar10-vgg11-functional-dualheat \
    split-cifar10-resnet18-functional-dualheat \
  --device cpu --no-download
```

Os diretórios de saída são distintos dos sweeps SlowHeat anteriores. Por
arquitetura, o relatório aplica Holm aos quatro contrastes primários
`DualHeat - SlowHeat`; métricas secundárias incluem FastHeat contra vanilla,
forgetting, task-aware, classifier gap, sinais por seed, bootstrap, tempo,
FLOPs e bytes de estado.

## Resultados pareados DualHeat concluídos

Os benchmarks VGG11 e ResNet18 foram concluídos com dez seeds pareadas e 13
métodos. Todos os checks de épocas, exemplos atuais, replay e histórico de
seleção foram registrados como iguais em cada contraste. Os próprios artefatos
mantêm o status `exploratory_paired_benchmark`.

Diferença de acurácia final Class-IL, sempre `DualHeat - SlowHeat`:

| Arquitetura | Par | Diferença média | IC95% t pareado | p ajustado de Holm |
|---|---|---:|---:|---:|
| VGG11 | `dualheat - slowheat` | -0,00483 | [-0,00892; -0,00074] | 0,08030 |
| VGG11 | `dualheat_lpr - slowheat_lpr` | +0,01430 | [0,00283; 0,02577] | 0,08030 |
| VGG11 | `dualheat_classifier_expander - slowheat_classifier_expander` | -0,01295 | [-0,02866; 0,00276] | 0,19027 |
| VGG11 | `dualheat_scroll - slowheat_scroll` | -0,00146 | [-0,02223; 0,01931] | 0,87717 |
| ResNet18 | `dualheat - slowheat` | -0,00007 | [-0,01252; 0,01238] | 1,00000 |
| ResNet18 | `dualheat_lpr - slowheat_lpr` | -0,00457 | [-0,01393; 0,00479] | 1,00000 |
| ResNet18 | `dualheat_classifier_expander - slowheat_classifier_expander` | -0,00496 | [-0,01825; 0,00833] | 1,00000 |
| ResNet18 | `dualheat_scroll - slowheat_scroll` | -0,00247 | [-0,01946; 0,01452] | 1,00000 |

Nenhum contraste permaneceu significativo a 5% após Holm. O único ganho médio
de FastHeat foi no par VGG11 com LPR, +1,43 ponto percentual, mas seu p ajustado
foi 0,08030. O resultado sustenta uma conclusão negativa/indeterminada: FastHeat
não trouxe melhoria robusta nas duas arquiteturas sob este protocolo.

vencedor a partir de um hash imutável do piloto. Isso limita a força de uma
alegação de pré-registro.
